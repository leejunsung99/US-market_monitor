# Ollama 운영 전환 (2026-10-23)

운영 경로는 중요도 필터 통과 → 기사/공시 본문 확보 → 로컬 Ollama 한국어 번역·요약 → 근거/숫자 검증 → 확정 양식 발송이다. Azure 키·리전·엔드포인트 설정과 Azure 호출 코드는 제거했다. `processors/translator.py`는 과거 스크립트 호환용 Ollama 별칭만 제공한다.

- `OLLAMA_BASE_URL=http://127.0.0.1:11435`
- `OLLAMA_MODEL=qwen3.5:9b`
- `OLLAMA_TIMEOUT_SECONDS=600`

프로젝트 GPU 서버는 `scripts/start_ollama_gpu.ps1`로 실행한다. Windows 운영 시작 시 위 주소의 서버가 내려가 있으면 같은 스크립트를 숨김 실행한다. 원격 Ollama 주소는 설정 검증에서 거부한다. 모델을 임의로 다운로드하거나 클라우드로 대체하지 않는다. 키가 필요하지 않으므로 Azure 리소스를 삭제해도 새 운영 경로에 영향이 없다.

모델 처리는 별도 단일 작업 스레드에서 진행한다. 수집 스케줄러와 SQLite 갱신/발송은 주 스레드에 남겨 긴 생성 중에도 다른 소스 수집을 계속한다. 생성 중인 알림은 `pending` 상태로 유지해 프로세스 중단 시 실제 발송 여부가 불명확한 알림으로 오인하지 않는다. Telegram 전송 직전에만 원자적으로 claim한다.

2026-10-26부터 운영 요약은 `ollama_grounded.py`를 사용한다. 원문 후보 문장마다 코드가 ID와 정확한 원문 위치를 부여하고, 모델은 항목마다 원문 ID 하나와 한국어 내용만 반환한다. 근거 인용문을 모델이 다시 작성하지 않는다. 서로 다른 문장의 수치를 한 항목에 섞지 않으며, 문장·항목 개수 제한 없이 중요한 내용을 선택한다. 긴 입력은 구간별로 모두 처리한다.

숫자·한국어·개조체와 함께 금액의 배율/통화, 실적 상회·하회 반전, 연간/전년 대비 혼동, 누락된 범위 끝값 등 자주 발견된 오류를 검증한다. 금액 토큰은 대소문자를 구분하지 않고 전체 단위를 보존한다. 영어 단어로 적힌 수량과 축약 월 이름도 숫자 비교에서 처리한다. `3 million=300만`, `$1 billion=10억 달러`는 Decimal로 정확한 크기를 비교하고, `top-10`, `5-10%`의 구분선을 음수 부호로 오인하지 않는다. 금액 범위 `$250-$275 million`의 공통 단위는 양 끝값에 적용한다. 명시적인 `to NEW from OLD`는 한국어 `OLD에서 NEW로` 순서로 복원한다. 이 검사는 모든 의미적 오류를 보장하는 일반적인 사실 검증기는 아니다.

검증된 항목과 실패 항목은 `source_metadata.ollama_work`에 저장한다. 재시도는 실패한 항목의 실제 원문만 다시 번역하고 기존 정상 항목을 재사용한다. 재시도 한 번에 복구 요청은 구간당 최대 두 번이며 남은 항목은 이후 재시도에서 이어간다. 검증되지 않은 항목이 남으면 전체 알림을 보류한다. 잘못 생성된 제목은 검증된 첫 항목으로 대체한다. 복구된 핵심 내용도 원문 순서로 복원한다.

요약 준비 실패는 `preparation_attempts`로 세고 Telegram 전송 재시도 횟수와 분리한다. 기사별 30초~15분 간격으로 알림 유효시간까지 재시도하며 다른 기사의 발송 대기 시간을 늘리지 않는다. 실제 Telegram 전송의 모호한 성공 여부·중복 방지 정책과 여덟 번 재시도 제한은 유지한다. 이미 확보한 본문은 재시도 때 다시 다운로드하지 않는다. 기본 유효시간 24시간은 발행 시각 기준이며, 긴 생성 중 유효시간이 지난 알림도 전송하지 않는다.

`source_metadata.ollama_summary`에 모델·입력 지문·정확한 근거 원문·검증된 결과·처리 시간을 보관한다. 동일 입력은 재사용하고 내용이 바뀌면 재생성한다. 사용자 메시지에는 모델명·처리 시간·검증 로그를 넣지 않는다. 출력은 국기, 굵게·밑줄 제목/카테고리, 개조체, 긴 항목 사이 빈 줄, 원문 및 채널 링크를 유지한다. 공시/기사/어닝콜/실적 일정 구분도 유지한다.

`processing_attempts` 테이블에 처리 성공·실패 원인·소요 시간을 보관하고, 마지막 원인은 `source_metadata.processing_failure`에도 기록한다. `python main.py --status`의 `pipeline_24h`에서 최근 24시간 신규 관측, 중요 후보의 발송 상태, 처리 성공 수·중앙 소요 시간·실패 원인, 마지막 발송 시각을 확인한다. 과거 버전 운영 기간의 처리 시도는 이 새 테이블에 소급 생성하지 않는다.

2026-10-26 검증: 자동 검사 341개 및 Ruff 통과, SQLite quick_check 정상. 실제 오라클 투자 기사 재생성 약 51초 후 분리된 테스트 큐에서 `Radar.dispatch` → 캐시 검증 → 테스트 채널 발송까지 확인했다(테스트 메시지 158). GPU 모델 전체가 VRAM에 올라간 상태도 확인했다. 복잡한 재무 기사에는 모델의 기간·비교 오역으로 보류되는 사례가 남아 있으며, 영문이나 검증되지 않은 부분 요약으로 대체 발송하지 않는다. 기존 실패 기사 전체의 복구율이 검증된 것은 아니다.

필터 버전 `2026-10-26.1`은 실적 발표 공지가 숫자 없는 API 요약만 갖고 있어도 본문 수집 단계로 넘긴다. 발표 전 예고·투자 권유는 제외한다. CapEx 변경, 명시적인 회사 성장 전망, 제품·메모리 로드맵 표현을 확장하고 계약·투자 최소 규모를 5억 달러에서 2.5억 달러로 낮췄다. 기존 보류 기사 30건의 읽기 전용 재판별에서는 테슬라 CapEx, 메타·램리서치·넷플릭스 실적, 마이크론 로드맵 등 5건이 추가 통과했다. 이는 전체 뉴스의 통과율 추정치가 아니라 보관된 검토 후보 표본의 결과다.

로컬 9B 모델은 즉시 결과를 반환하는 엔진이 아니다. 실제 GPU 검증에서 단문은 최초 모델 로딩 포함 약 95초, 긴 기사 첫 생성은 약 192초, 실패 항목만 재생성한 추가 처리는 약 50초였다. 기사 길이·GPU 부하·모델 상주 여부에 따라 달라진다. 단일 생성 작업을 사용하므로 알림이 몰리면 대기열이 생길 수 있다.

검증 자료는 `data/ollama-production/`에 보관한다. `verify_ollama_pipeline.py`는 운영 DB의 복사본과 테스트 채널만 사용해 실제 `Radar.dispatch`의 백그라운드 처리·캐시·발송을 확인하며, 본 채널의 과거 알림을 재발송하지 않는다. 기존 Azure 기반 발송 이력과 편집 알림은 변경하지 않는다.
